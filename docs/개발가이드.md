# 개발가이드

모듈 트리·의존 방향·실행 방법은 [README](../README.md), 애그리거트별 규칙은 [도메인모델](도메인모델.md) 참고. 이 문서는 모듈 역할과 코드 작성 규칙의 기준 문서다.

## 모듈별 역할

### adapter

| 모듈 | 방향 | 역할 |
|---|---|---|
| `inbound:controller` | inbound | REST API |
| `inbound:listener` | inbound | Kafka 메시지 수신 |
| `inbound:event` | inbound | 같은 트랜잭션 안의 내부 도메인 이벤트 수신 |
| `outbound:repository` | outbound | outbound repository 포트 구현 |
| `outbound:producer` | outbound | `DomainEventPublisher` 구현 |

어댑터는 입력·출력 채널 단위로 나눈다. 같은 Kafka 를 쓰더라도 수신(`listener`)과 발행(`producer`)은 다른 모듈이다.

### infrastructure
어댑터가 사용하는 기술 설정만 둔다. 비즈니스 코드는 두지 않는다.
- `h2`: 데이터소스 설정, H2 드라이버
- `kafka`: 공통 `KafkaTemplate`, consumer container factory, 에러 핸들러

각 모듈의 `src/main/resources/config/*.yml` 은 `common:yaml-config` 의 `EnvironmentPostProcessor` 가 기동 시 자동 로딩한다. 모듈별 설정(DB, Kafka, outbox)은 server 가 아니라 해당 모듈에 둔다.

### server
서버별로 조합하는 어댑터.

| 모듈 | inbound | outbound |
|---|---|---|
| `api` | controller, event | repository, producer |
| `consumer` | listener, event | repository, producer |

### architecture-test
`HexagonalArchitectureTest` 가 ArchUnit 으로 아래 규칙을 검증한다. 위반 시 빌드 실패. 새 애그리거트 의존을 추가하면 이 테스트가 깨질 수 있다.
- 헥사고날 계층 의존 방향 (`hexagonalArchitecture`)
- 애그리거트 간 순환 의존 금지 (`aggregateFreeOfCycles`, `applicationAggregateFreeOfCycles`)
- 애그리거트 간 허용된 의존 (`aggregateDependencies`)

### build-plugin, common (included build)
`settings.gradle.kts` 에서 `includeBuild` 로 포함한다.
- `build-plugin`: 모듈 공통 빌드 설정을 convention plugin(`sample-kotlin-jvm`, `sample-springboot`)으로 제공한다
- `common`: 프로젝트와 무관하게 재사용할 수 있는 라이브러리 (`utils`, `json`, `yaml-config`, `actuator`)

## 패키지
```
com.sample.hexagonal.sample
├── domain
│   ├── {aggregate}               // 애그리거트별 패키지
│   │   └── event                 // 해당 애그리거트의 도메인 이벤트
│   └── event                     // DomainEvent, AggregateRoot(enum)
├── application
│   ├── service
│   │   └── {aggregate}
│   │       ├── port/inbound      // 어댑터가 호출하는 유스케이스 인터페이스 + 요청 DTO
│   │       ├── port/outbound     // 서비스가 필요로 하는 인터페이스
│   │       └── spi               // 다른 애그리거트가 구현하는 인터페이스
│   └── support                   // DomainEventPublisher, 공통 예외, 토픽
└── adapter                       // 모듈별 역할 참고
```
- `domain/{aggregate}` 와 `application/service/{aggregate}` 를 슬라이스라 부르고, 같은 이름의 두 슬라이스를 묶어 애플리케이션 컴포넌트라 한다
- 값 객체도 사용하는 애그리거트 패키지에 둔다 (예: `{aggregate}.Email`)

## 애그리거트와 애플리케이션 컴포넌트 의존관계
- 애그리거트는 다른 애그리거트 루트를 직접 참조할 수 있다(`@ManyToOne` 객체 참조). 조회 메서드는 사용할 수 있지만 다른 애그리거트를 변경하는 메서드는 호출하지 않는다
- 애플리케이션 서비스는 다른 애그리거트의 inbound 포트(주로 `Finder`)와 요청 DTO 만 사용한다. 구현 클래스는 직접 참조하지 않는다
- 슬라이스 간 순환 의존은 허용하지 않는다. 순환이 생기면 호출하는 쪽이 `spi` 인터페이스를 정의하고 상대가 구현한다
  - 예: `course.spi.CurriculumValidator`(course 가 정의) ← `curriculum.CurriculumValidationService`(curriculum 이 구현)

## 애그리거트 설계 기준

### 애그리거트 판정

- 애그리거트 = 일관성 경계. 기본은 분리, 작게 설계
- 합치는 유일한 기준: 한 트랜잭션에서 즉시 지켜야 하는 불변식이 있는가
  - 같이 저장된다 / 개념적으로 포함된다 / 생명주기가 같다 → 기준 아님
- 한 트랜잭션은 하나의 애그리거트만 변경. 애그리거트 간 일관성은 도메인 이벤트로 결과적 일관성
  - 예외: 생성 직후 함께 만들어져야 하는 경우처럼 즉시 일관성이 필요하면 같은 트랜잭션의 내부 이벤트(`publishInternalEvent`)로 처리할 수 있다. 케이스별로 결과적 일관성(커밋 후 처리·outbox)과 비교해 선택한다
- 분리 신호 (ex. Course ↔ Curriculum)
  - 수정 시점이 다르다 (가격·상태 vs 섹션·수업)
  - 함께 로딩하기엔 크다
  - 재사용되거나 독립적으로 버전 관리된다
  - 외부(수강·진도)가 내부 엔티티(수업)를 직접 참조해야 한다
    → 애그리거트 내부 엔티티는 외부에서 직접 참조하지 않는 것이 원칙

### 연관관계 매핑

- 애그리거트 간
  - `@ManyToOne` 단방향 또는 ID 참조
  - cascade 금지, 다른 애그리거트의 변경 메서드 호출 금지
- 애그리거트 내부
  - 루트가 자식 컬렉션을 소유하면 `@OneToMany` 허용
  - 생명주기는 `cascade = ALL` 로 루트에 묶는다. 삭제는 soft delete(`deleted = true`)로 처리하므로 `orphanRemoval` 은 쓰지 않는다
  - 애그리거트 내부 `@OneToMany` 는 `mappedBy` 양방향을 기본으로 한다
    - 단방향은 중간 테이블이 생기거나(`@JoinColumn` 없음), FK 를 채우는 UPDATE 가 추가로 나간다(`@JoinColumn`)
    - 양쪽 참조는 루트의 도메인 메서드에서 함께 맞추고, 자식의 생성자·변경 메서드는 `internal` 로 막는다

## 포트
- **inbound**: 어댑터가 호출하는 유스케이스. 예) `{Aggregate}Creator`, `{Aggregate}Finder`
  - 구현체는 같은 슬라이스의 `~Service` (`{Aggregate}ModifyService`, `{Aggregate}QueryService`)
  - 어댑터는 구현체가 아닌 포트 인터페이스에 의존한다
- **outbound**: 서비스가 의존하는 인터페이스. 예) `{Aggregate}Repository`, `EmailSender`
  - 구현은 adapter 가 담당한다
- 도메인이 필요로 하는 기술 추상화는 도메인에 인터페이스, adapter 에 구현을 둔다 (예: 도메인의 `PasswordEncoder` 인터페이스 ← adapter 모듈의 구현)

## 도메인 모델 관례
- JPA 엔티티가 곧 도메인 모델이다(별도 영속 모델 없음). domain 의 외부 의존은 `jakarta.persistence-api` 뿐이다
- 엔티티는 `AbstractEntity` 상속 → `id`, `createdAt`, `updatedAt`, `deleted` 공통 제공
- 애그리거트 루트에는 `@AggregateRoot` 를 붙인다
- 생성은 의미 있는 이름의 정적 팩터리 메서드로 한다: `Member.register(...)`
  - 생성자는 `protected`(루트) 또는 `internal`(내부 엔티티)로 막는다. JPA 기본 생성자는 `kotlin("plugin.jpa")` 가 만든다
- 상태 변경은 의미 있는 도메인 메서드로만 한다(예: `activate()`, `updateInfo()`). 프로퍼티는 `protected set`
- 상태를 바꾸는 메서드는 `markUpdated()` 를 호출해 `updatedAt` 을 갱신한다 (`@PreUpdate` 사용 안 함)
- 불변식은 메서드 진입 시 `check(...)`(상태) / `require(...)`(인자)로 검증한다
- 값 객체는 `@Embeddable data class` + `init` 블록에서 검증한다 (예: `Email`, `Profile`)
- 애그리거트 내부 엔티티의 변경 메서드는 `internal` 로 막고 루트를 통해서만 바꾼다 (예: 커리큘럼의 `Section`, `Lesson`)
- 삭제는 soft delete: 루트가 `markDeleted()` 로 표시한다. 조회 시 제외 조건은 adapter 쿼리에 둔다

## 애플리케이션 서비스 관례
- 변경 서비스: `@Service @Transactional @Validated`, 조회 서비스: `@Service @Transactional(readOnly = true)`
- 조회 전용 서비스와 변경 서비스를 분리한다 (`{Aggregate}QueryService` / `{Aggregate}ModifyService`)
- 입력 검증은 inbound 포트 메서드 파라미터에 `@Valid`, 요청 DTO 에 Bean Validation 제약
- 도메인 규칙은 도메인에, 조율·중복검사·트랜잭션 경계는 서비스에
- 같은 애그리거트 조회 후 없으면 예외: `repository.findById(id).getOrThrowNotFound(id)` (서비스에서 처리)

## 도메인 이벤트
- 이벤트는 저장 후 서비스에서 생성한다 (`IDENTITY` 전략이라 저장 전에는 id 가 없다)
- `DomainEventPublisher.publishInternalEvent`: 같은 트랜잭션 안에서 `adapter:inbound:event` 리스너가 처리. 리스너 실패 시 함께 롤백
- `DomainEventPublisher.publishExternalEvent`: Namastack outbox 에 저장 후 커밋되면 Kafka 로 발행. 최소 한 번 전달이므로 consumer 는 멱등해야 한다
- 토픽 라우팅은 `adapter:outbound:producer` 의 `NamastackConfig`(`InternalTopic.from(event)`), 폴링·재시도 설정은 같은 모듈의 `config/outbox.yml`
- 토픽 이름은 `AggregateRoot` enum 이름과 같다. 애그리거트를 추가하면 enum 값과 `@KafkaListener` 용 `InternalTopic` 상수를 함께 추가한다

## 어댑터 관례
- 응답 DTO 는 adapter 의 `dto` 패키지에 `data class` 로 두고 `of(...)` 정적 팩터리로 변환한다
- 예외 처리는 `ApiControllerAdvice` 에서 `ProblemDetail` 로 통일
- outbound repository 포트는 Spring Data `Repository<T, ID>` 인터페이스가 직접 상속해 구현한다. 필요한 메서드만 선언

## 데이터 전달 객체
- 요청 DTO(`{Aggregate}{Action}Request`)는 inbound 포트 패키지에 둔다. 도메인 생성 인자가 많아지면 `toInfo()` 로 도메인 입력 객체(`{Aggregate}Info`)로 변환해 전달한다
- 도메인은 요청 DTO 를 직접 받지 않는다

## 테스트 관례
- Kotest `StringSpec` + mockk. Spring 테스트는 springmockk 의 `@MockkBean`
- Spring 테스트가 있는 모듈은 `src/test/kotlin/io/kotest/provided/ProjectConfig.kt` 로 `SpringExtension` 을 등록한다
- 테스트 데이터는 domain testFixtures 의 애그리거트별 fixture(`{Aggregate}Fixture`)를 `testImplementation(testFixtures(project(":domain")))` 로 사용한다
- 계층별 진입 애노테이션
  - application: `@ApplicationServiceTest` (`@SpringBootTest` + `@Transactional`, 이벤트는 `RecordingDomainEventPublisher` 로 기록)
  - repository: `@RepositoryTest`
  - 웹: `@WebMvcTest`
  - 서버 통합: `server:api` 의 `@SpringBootTest`

## 네이밍
- inbound 포트: 동작 주체 명사 (예: `MemberRegister`, `MemberFinder`)
- 서비스 구현: `<도메인><책임>Service` (`{Aggregate}ModifyService`, `{Aggregate}QueryService`)
- outbound 포트: `<도메인>Repository`, `<기능>Sender`
- 이벤트: `<도메인><과거분사>Event` (예: `MemberRegisteredEvent`)
- 이벤트 리스너: `<도메인>DomainEventListener` (inbound:event), `<도메인>Listener` (inbound:listener)
- 예외: `<상황>Exception` (예: `DuplicateEmailException`)
