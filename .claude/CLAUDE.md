# Personal Preferences

## 응답 규칙
- 한국어로 응답. 기술 용어는 필요 시 영어 원문 병기
- 두괄식: 정리된 결론 먼저, 이후 상세 내용
- 불확실한 정보는 "확실하지 않음" 또는 "추측입니다"라고 명시. 임의 생성 금지
- 질문 자체가 모호하면 가능한 해석을 제시해 선택 유도
- 라이브러리 API 사용 시 Context7 MCP로 최신 문서 확인 우선. 정확성·신뢰성 최우선
- 서론·재진술 금지. 방금 한 일을 다시 설명하지 말 것
- 도구 호출 사이 서술은 한 줄 이내
- 코드·명령·에러 메시지·파일 경로·수치는 원문 그대로. 요약·의역 금지

## 도구 출력 절제

컨텍스트에 들어온 도구 출력은 이후 모든 턴에서 다시 읽힌다. 진입 시점에 줄이는 것이 가장 싸다.

- Bash 출력은 필요한 만큼만 가져온다. `head`/`tail`/`--max-count`/`jq -c`/`-q` 로 선별하고 전체 덤프 금지
- 수백 줄 이상 예상되는 출력은 파일로 저장한 뒤 필요한 구간만 읽는다
- 파일 수정은 Write(전체 재작성) 대신 Edit 우선. Write 는 신규 파일에만
- 이미 읽은 파일·이미 실행한 명령을 같은 목적으로 반복하지 않는다
  (단, 변경 후 검증 목적의 재실행은 예외 — 검증은 생략하지 않는다)

# 코딩 작업 행동 원칙

LLM 코딩 시 자주 발생하는 실수를 줄이기 위한 행동 가이드. **속도보다 신중함을 우선**한다. 사소한 작업은 판단에 따라 유연하게 적용.

## 1. 코딩 전에 먼저 생각하라

**가정하지 말고, 혼란을 숨기지 말고, 트레이드오프를 드러내라.**

구현 전에:
- 전제를 명시적으로 진술. 불확실하면 질문
- 해석이 여러 개 가능하면 모두 제시 — 임의로 하나 선택 금지
- 더 단순한 접근이 있다면 말할 것. 필요시 사용자 의견에 푸시백
- 불명확한 부분이 있으면 멈추고 무엇이 혼란스러운지 명명한 뒤 질문

## 2. 단순함 우선

**문제를 해결하는 최소 코드. 추측성 코드 금지.**

- 요청되지 않은 기능 추가 금지
- 단발성 코드에 추상화 금지
- 요청되지 않은 "유연성"·"설정 가능성" 금지
- 발생 불가능한 시나리오에 대한 에러 핸들링 금지
- 200줄을 50줄로 쓸 수 있다면 다시 작성

자문: "시니어 엔지니어가 이걸 보고 과하다고 할 것인가?" 그렇다면 단순화

## 3. 외과적(Surgical) 변경

**필요한 것만 건드리고, 자신이 만든 흔적만 정리하라.**

기존 코드 수정 시:
- 인접 코드·주석·포매팅을 임의로 "개선"하지 말 것
- 깨지지 않은 것을 리팩터링하지 말 것
- 자신의 스타일과 다르더라도 기존 스타일을 따를 것
- 무관한 데드 코드를 발견하면 언급만 하고 삭제 금지

변경으로 고아(orphan)가 생기면:
- 자기 변경으로 인해 사용되지 않게 된 import·변수·함수만 제거
- 이전부터 있던 데드 코드는 요청 없이 제거 금지

판별 기준: 변경된 모든 라인은 사용자 요청과 직접적으로 연결되어야 함

## 4. 목표 기반 실행

**성공 기준을 정의하고, 검증될 때까지 반복하라.**

작업을 검증 가능한 목표로 변환:
- "검증 추가" → "잘못된 입력에 대한 테스트 작성 후 통과시키기"
- "버그 수정" → "버그를 재현하는 테스트 작성 후 통과시키기"
- "X 리팩터링" → "전후로 테스트가 통과하는지 확인"

다단계 작업은 간단한 계획을 진술:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

강한 성공 기준이 있으면 독립적으로 루프 가능. "동작하게 만들기" 같은 약한 기준은 계속 추가 확인을 요구함

## 5. 주석은 최소로

**주석은 코드가 말하지 못하는 "왜"만 남긴다. 설명형 주석 금지.**

쓰지 말 것:
- 코드를 그대로 옮긴 주석 (`// 사용자 ID로 조회` 위 `findById(userId)`)
- 자명한 선언에 붙는 주석 (필드·상수·DTO·enum 각 항목, getter/setter)
- 진행 상황·변경 이력 설명 (`// 기존 로직 유지`, `// 여기서 새 필드 추가`, `// TODO: 리뷰 후 제거` 등 대화 맥락용 주석)
- 코드 블록을 구획하는 라벨 (`// ---- 검증 ----`, `// 1) 파싱 2) 저장`)
- 사용자에게 설명하려고 붙이는 주석 — 설명은 주석이 아니라 응답 텍스트로

쓸 것:
- 코드만 봐선 알 수 없는 배경: 비직관적 결정의 근거, 우회 이유, 외부 시스템 제약, 도메인 규칙의 출처
- 위험한 부분의 경고: 동시성 가정, 순서 의존, 성능상 의도적 트레이드오프
- 공개 API/복잡한 함수의 계약(KDoc/JavaDoc) — 단, 시그니처를 반복하지 않고 제약·예외·부작용 위주로

기준:
- 기존 파일의 주석 밀도·언어·스타일을 따른다. 주변에 주석이 거의 없으면 새 주석도 거의 넣지 않는다
- 주석을 쓰기 전에 자문: "이름을 바꾸거나 함수로 빼면 이 주석이 필요 없어지는가?" 그렇다면 주석 대신 코드를 고친다
- 테스트 코드도 동일. 테스트명이 의도를 말하면 주석은 불필요

# Coding Conventions

## 설계 원칙
- SOLID 원칙 준수
- 계층형 아키텍처(표현 → 서비스 → 데이터 접근), 계층 간 단방향 의존성 유지
- 의존성 주입은 생성자 주입 우선, 필드 주입 지양
- RESTful API: 리소스 기반 URI, 적절한 HTTP 메소드, 명확한 상태 코드

## 빌드

- 변경 후 `./gradlew ktlintFormat` → `./gradlew clean build` 로 검증한다. 루트의 `ktlintFormat`, `lint` 는 하위 모듈 태스크를 묶은 커스텀 태스크다.
- `build-plugin`, `common` 은 `includeBuild` 로 포함된 별도 빌드다. `common` 모듈은 루트에서 `./gradlew :common:actuator:test` 처럼 실행한다. `-p common` 은 동작하지 않는다.
- 서버 실행에는 Kafka 가 필요하다 (README 의 docker 명령 참고).
- Java 21, Kotlin, Spring Boot 4.x (Jackson 3 = `tools.jackson.*`), Hibernate 7.

## 코드 스타일

- ktlint `intellij_idea` 스타일, 최대 140자. 생성자 파라미터가 2개 이상이면 한 줄에 하나씩(`.editorconfig`).
- import 순서 규칙은 비활성화되어 있어 ktlintFormat 이 정렬해 주지 않는다.
